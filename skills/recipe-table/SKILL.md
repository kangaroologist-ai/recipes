# 配方表

把一份食谱整理成 YAML，再用 `scripts/render_recipe.py` 渲染成三部分：Cooking for Engineers 式配方表（材料在左，步骤是向右合并的格子）、按依赖关系排出的时间线、每份的营养成分表。YAML 是唯一的源文件，三种输出都从它生成，所以改配方只改 YAML。

## 流程

1. **拿到原文**
   - 文字或截图：直接读。网页链接：用 WebFetch。
   - YouTube：云端抓字幕会被 YouTube 拦。先看简介里有没有配方；需要字幕时，用户电脑已连接就用浏览器打开视频读文字稿，否则请用户把“显示文字稿”的内容复制过来。

2. **先确认做法，再做表**：做法还在讨论、或者是你帮用户设计的（用量、温度、时间里有你的建议），先用文字把做法讲清楚、列出要确认的点，等用户确认了再往下做，哪怕用户说的是“出个 recipe”。用户贴来现成的食谱要整理，或做法已经确认过，才直接做表。表里写用户实际的做法和用户的叫法：他烤 60 分钟就写 60，不换成你建议的参数；他叫“帕玛森干酪”“一夜干”就这么写。

3. **写 YAML**，存到 scratchpad 的 `recipes/<slug>.yaml`。字段和规则见 `references/yaml-format.md`，第一次写之前读一遍；`assets/examples/` 里有两个完整示例可以照着改。内容怎么取舍见下面“表里写什么”，这是最容易做错的部分。

4. **填营养数据**：每个材料一个 `nut`（这份用量对应的 6 个数）。有 nutrition-logger 工具时先用 `search_food` 查用户自己的食物库，因为用户实际用的产品最准；查不到再用 `lookup_nutrition` 按用量折算。盐、泡打粉也要算钠，代糖按 0 kcal。缺任何一个 `nut` 就不出营养表，回复里说明缺哪个。

5. **渲染**（需要 PyYAML，缺就 `pip install pyyaml --break-system-packages`）：

   ```bash
   python3 <本 skill 目录>/scripts/render_recipe.py recipes/<slug>.yaml recipes/<slug>.widget --widget
   ```

   脚本会检查结构（字段名拼错、材料没用到、被用两次、终点不止一个、顺序不对等），报错就按提示改 YAML 再跑。

6. **自查**：结构通过不等于表是对的。显示之前逐格过一遍，任一条不对就改 YAML 重新渲染：
   - 每个步骤格：去掉它，照着做的人会不会漏事？不会就删掉或并进相邻的步骤。
   - 每条小字：不写它，做出来会不会不一样？不会就删。
   - 材料从上到下是不是先用的在上；名称里有没有括号、描述、品牌。
   - 时间线默认只有一个人做：两件要动手的事不会同时出现。脚本按这个规则排，如果排出来不合理，多半是 `passive` 标错了。
   - 每一步的时长和名称对得上（化黄油本身半分钟，2 分钟的是“热锅”）；热锅结束正好接上要用它的那一步。
   - 图片要用 Read 看一眼：有没有文字重叠、错位，有没有哪一格明显比它的内容宽得多。

7. **显示**：读取 `.widget` 文件，把内容原样作为 `widget_code` 传给 visualizer 的 `show_widget`（第一次用前先调 `read_me`，platform 按设备选）。没有 visualizer 的环境就出图片，把文件附给用户。不要手改 HTML，样式问题改脚本，否则下次又回到旧样子。

8. **回复**：widget 外用一两句话说总时长、哪些时长或营养数据是估的。表格里已有的内容不要再用文字重复。

## 表里写什么

配方表的好处是一眼看完：谁和谁在一起、按什么顺序、做什么。所以格子越少、字越少越好，能从结构看出来的都不写。下面每条都是用户看过表后提的意见。

**步骤**

- 只有真正的操作才占一格：切、磨碎、搅匀、煎、烤、煮、拌。切半、磨碎这类处理写成步骤，不写成材料的描述（不写“小番茄（切半）”“帕玛森碎”）。用户实际没做的处理不写（罗勒是整片放的，就没有“撕碎”）。
- 顺手就做了的动作不单列：擦干、抹盐、摆进烤盘、放上去、涂抹、出炉、取出。确实要提醒的，写进相邻步骤的小字。
- 不用材料的准备不进表：预热烤箱、烧水。温度写在烤那一步的小字里（`170°C`）。热锅抹油、化黄油这类用到材料、又占一段时间的保留，写法见 `references/yaml-format.md` 规则 5。
- 连着做、中间没有新东西加进来的几步合成一格，时长相加：铺盘 + 烤 60 分钟 + 静置 10 分钟写成“烤 · 70 min”。
- 提前一天做的（一夜干、隔夜腌）用一个 `ahead` 步骤，名称用用户的叫法，过程写在小字里（`擦干抹盐 · 冷藏风干`）。
- 配菜和主食（意面、米饭）只占一个材料加一个“煮”，不展开水、盐、锅。
- 每个步骤只写一个动词，中英文都用菜谱里的常用说法；不确定的词（比如 fold 和 stir 的区别）先想清楚再用，拿不准就问用户。

**小字（`note`）**

- 默认不写。只留不写就会做错、又没法从表里看出来的：温度、火候、“加盖”、“皮朝上”、“留半杯面水”。
- 不写原因和效果（“番茄先烤软”）、不写判断熟度的指标（“80°C 出炉”）、不写常识（“水提前烧开”“少放盐”）、不写可有可无的技巧（“奶酪分两次加”）。这些想说就在回复里说一句。
- 说清楚谁放哪：写“鸡腿皮朝上放最上面”，不写“放上”。
- 不写“等待”，等待的步骤靠颜色区分。

**材料**

- 用通用名，不写品牌或型号（品牌需要时写进 `src`）；用户有固定叫法、或者东西有正式名字的，用那个名字（Cavatappi，不写“螺旋意面”）。
- 材料格只放名称和一个用量：不写“估”“一大把”“隔夜冷饭”“干重”这类说明；“3 勺”和克数只留一个（按原文）；盐、胡椒这类调味写“适量”。`note` 只留换算和比例这类会用到的（“共约 350 g”“鸡重的 2%”）。估的用量和营养依据写进 YAML 注释或 `src`，在回复里说明。
- 同一种材料分两次用，拆成两个材料，名称完全一样，不加括号、不写“一半”“铺底用”：它们各自接到哪一步，表上看得出来。同一步里用的同一种材料合成一个（两处橄榄油都进烤盘，就写一行 15 ml）。
- 一个材料要切开走两条路时（鸡蛋分蛋黄蛋清、小葱分葱白葱绿），材料表里写整个的，再用带 `out` 的分离步骤分开。同时放的调味（盐和白胡椒）合成一行。
- 上下顺序由脚本按动手先后排（先用的在上，提前一天的在最上），YAML 里不用费心排。排出来和用户的习惯不一样时，用 `after` 调步骤的先后，不要去改脚本。

**其他**

- 菜名简洁，用用户的叫法。
- 原文没写时长就按常识估，回复里说明哪些是估的。
- 开火的步骤写 `phase: heat`，不用一直动手的步骤写 `passive: true`。

## 其他输出

同一个命令换最后的参数：

- `--png`：完整图片（标题、配方表、时间线、营养表）。
- `--table-png`：只有标题、摘要行和配方表的图片，适合发给别人。加 `--en` 出英文版，需要 YAML 里有 `*_en` 字段（见 `references/yaml-format.md`），缺了脚本会列出来。
- 用户要“图片”时默认给三张：`--png`、`--table-png`、`--table-png --en`。图片是 2 倍分辨率，用 Chrome / Chromium 渲染（自动找，找不到可设环境变量 `RECIPE_CHROME`），没有时退回 `wkhtmltoimage`；还需要 Noto Sans CJK 字体，没装的话字形和列宽会有出入。生成后先用 Read 看一眼，再把文件附给用户。
- `--md`：GitHub Markdown（合并格表格 + Mermaid 甘特图 + 营养表），放进 repo 用。
- `--page`：独立 HTML 页面。

## 改样式时

用户已经逐条确认过现在的样式，记录在 `references/style.md`。改 `render_recipe.py` 之前先读它，改完用 `assets/examples/` 里两个示例把 `--widget` 和 `--png` 都跑一遍，确认没破坏已确认的部分。新定下来的样式记进 `style.md`，新的内容取舍记进上面“表里写什么”。
